Simple regression

Week 3 found a correlation between finger length and reaction time — whatever its strength turned out to be. Today: turn that into a model, and be honest about what it’s worth.

From correlation to formula

Week 3 found a correlation between finger length and reaction time. HR wants to know: can we turn that into an actual formula — a screening tool?

In other words the firm wants to measure a candidate’s finger length, plug it into our fitted line, and use the predicted reaction time to decide whether to shortlist them — no need to run the real 10-trial test at all. Ethics clearly not a huge concern at this firm.

Naive answer: draw a line through the points, read off the equation, done.

Why it’s not that simple: which line, by what criterion? What does the slope actually mean? And a correlation doesn’t become a good predictor just because you fit a line through it — how good it is depends on how strong that correlation actually was.

What is regression?

Two goals, kept separate

  • Predictive analysis — what to expect of y for a given x. Concerned with the predicted value.
  • Causal analysis — the effect of x on y. Concerned with a parameter — what would y be if we changed x?

Regression itself doesn’t know which goal you have. It’s a method of comparison either way — the interpretation you’re allowed to make is what changes.

Regression: comparing conditional means

Regression uncovers the pattern of association between y (the outcome we care about) and x — by comparing the average value of y across different values of x.

\[E[y \mid x] = f(x) \qquad \text{shorthand: } y^E = f(x)\]

  • Non-parametric regression — no functional form imposed; flexible, but needs many observations per x value (this is exactly the bin-scatter from Week 3)
  • Parametric regression — imposes a functional form (e.g. linear); more restrictive, but interpretable with far less data

Source: Békés & Kézdi (2021), Data Analysis for Business, Economics, and Policy, Ch. 7

Non-parametric regression: LOWESS

Bin-scatter gives one average per bracket. LOWESS (locally weighted scatterplot smoothing, “loess”) gives a smooth curve instead — a predicted value at every x, not just at bin midpoints.

  • It’s a moving, weighted local average: points near x count a lot, points far from x count little
  • The bandwidth controls how “local” — wide = smoother, but can miss real bends; narrow = tracks the pattern closely, but looks rugged
  • Like bin-scatter: great for spotting shape, gives no interpretable number

LOWESS can be estimated in most stats packages, including Python — this is where we start showing the actual code behind what we’re building, alongside the ideas. In Python, that’s statsmodels: statsmodels.nonparametric.smoothers_lowess.lowess.

Source: Békés & Kézdi (2021), Ch. 7

Linear regression

From y to \(y^E\)

Every individual observation’s y is really:

\[y = \alpha + \beta x + \varepsilon\]

  • \(\varepsilon\) is everything else affecting y — other factors, individual noise, luck. We never observe it directly.
  • Key assumption: \(E[\varepsilon \mid x] = 0\) — on average, the error is unrelated to x; x tells us nothing about which way \(\varepsilon\) leans.

Take the expectation of both sides:

\[E[y \mid x] = \alpha + \beta x + \underbrace{E[\varepsilon \mid x]}_{=\,0} = \alpha + \beta x\]

The error term doesn’t vanish from reality — it averages to zero by assumption. What’s left is exactly \(y^E\): our shorthand for “the part of y that x explains, once the noise is averaged away.”

Individual students will still scatter around this fitted line by their own \(\varepsilon\) — finger length isn’t the only thing driving reaction time. \(y^E\) is the average; any one student’s actual reaction time differs from it by their own \(\varepsilon\).

Source: Békés & Kézdi (2021), Ch. 7

Imposing a line

\[y^E = \alpha + \beta x\]

  • Linear regression imposes linearity in the coefficients — the simplest parametric form
  • Two coefficients: the intercept (\(\alpha\)) and the slope (\(\beta\))
  • Linearity is an assumption, or an approximation — even if the true pattern curves, a line approximates its average slope

\(\alpha\): the average value of y when x is zero —

\[E[y \mid x=0] = \alpha + \beta \times 0 = \alpha\]

\(\beta\): the expected difference in y for observations one unit apart in x —

\[E[y \mid x=x_0+1] - E[y \mid x=x_0] = \big(\alpha + \beta(x_0+1)\big) - \big(\alpha + \beta x_0\big) = \beta\]

Precise language matters

Good ways to say what \(\beta\) means: “y is higher, on average, by \(\beta\) for observations with a one-unit higher x.”

Avoid “increases/decreases” — implies something changing over time. Avoid “effect” — implies causation. Neither is justified by a regression alone, on observational data.

Source: Békés & Kézdi (2021), Ch. 7

Regression on a binary x

Simplest case: x is 0/1 — like device (Laptop = 0, Phone = 1).

  • \(\alpha\) = average y when x = 0 (average reaction time on Laptop)
  • \(\beta\) = difference in average y between x = 1 and x = 0 (Phone minus Laptop)
  • \(\alpha + \beta\) = average y when x = 1 (average reaction time on Phone)
  • The regression line is just two points, connected

Source: Békés & Kézdi (2021), Ch. 7

The OLS estimator

The slope formula

\[\hat\beta = \frac{Cov[x,y]}{Var[x]}\]

  • The covariance between x and y, normalised by the variation in x
  • Measures the covariance relative to how spread out x is
  • That’s why it can be read as “difference in average y per unit difference in x”

Source: Békés & Kézdi (2021), Ch. 7

The intercept formula

\[\hat\alpha = \bar y - \hat\beta \bar x\]

  • Average y, minus average x scaled by the slope we just found
  • A direct consequence: rearrange it and you get \(\bar y = \hat\alpha + \hat\beta \bar x\) — the fitted line always passes through the point \((\bar x, \bar y)\), the average of averages
  • Once \(\hat\beta\) is fixed, \(\hat\alpha\) isn’t a second independent choice — it’s whatever pins the line through that point

Source: Békés & Kézdi (2021), Ch. 7

Every point’s rectangle, from the (x̄, ȳ) crosshair to the point, has area \((x_i-\bar x)(y_i-\bar y)\) — exactly the term averaged inside \(Cov[x,y]\). Blue rectangles push the covariance positive; red ones pull it negative. Cov[x,y] is the net signed area.

Var[x] is the same idea, applied to x alone

\(Var[x] = Cov[x,x]\) — the identical rectangle idea, but pairing x with itself. Since a number times itself is never negative, every “rectangle” is the same colour: Var[x] is always positive, a pure measure of x’s own spread.

\(\hat\beta\) = (net signed area between x and y) ÷ (x’s own spread) — literally, how much x and y move together, relative to how much x moves on its own.

Why divide by Var[x] at all?

Imagine measuring finger length in different units (mm → cm is ×0.1). Cov[x,y] and Var[x] would both change, a lot — but should the slope itself?

The slope expressed per original mm doesn’t change. That’s the whole point of dividing by Var[x] — without it, “the slope” would depend on which ruler you happened to use.

Why this particular line?

The residual for an observation is the gap between its actual y and what a candidate line predicts: \(y_i - (\alpha + \beta x_i)\). OLS chooses \(\hat\alpha, \hat\beta\) to minimise the sum of squared residuals:

\[\min_{\alpha,\beta} \sum_{i=1}^n (y_i - \alpha - \beta x_i)^2\]

Solving this with calculus gives exactly the Cov/Var formula — we won’t derive it here (see the textbook, U7.1, if you’re curious). Instead, let’s watch it being the minimum.

OLS is BLUE

Best Linear Unbiased Estimator — among every linear, unbiased way of estimating \(\beta\), OLS has the smallest variance. “Best” here means most precise, not most correct.

The Gauss-Markov theorem states that OLS is BLUE only if a handful of assumptions about the data are true.

What has to be true?

  • Linearity — a straight line is a reasonable approximation
  • Independent observations — one observation’s error doesn’t leak into another’s
  • Homoskedasticity — the spread of residuals is roughly constant across the range of x, not fanning out or narrowing
  • No extreme influence — no single point is silently dragging the whole line
  • No perfect multicollinearity — no explanatory variable is an exact linear combination of the others, or OLS can’t even be computed. Only really bites once there’s more than one x — full treatment in Week 6.

These five are what BLUE requires — Gauss-Markov doesn’t care what shape the residuals take. There’s a sixth assumption, normally distributed residuals, that never appears on a BLUE checklist: it can’t make \(\hat\beta\) biased or imprecise. It only matters once we build a confidence interval or t-test around \(\hat\beta\) — which is where Week 5 starts.

Homoskedasticity, concretely: if slower reactors are also more erratic trial-to-trial — plausible, given reaction time’s right skew from Week 1 — the spread of residuals would fan out for higher predicted values instead of staying constant.

None of these make OLS wrong if violated — but they change how much you should trust the standard errors and the line’s precision. Homoskedasticity in particular gets a full treatment next week, when we build confidence intervals for \(\hat\beta\) itself. No extreme influence — the fourth assumption — gets its own live demonstration later this session, in “Influential observations.” One assumption doesn’t even make this list: whether the residuals are normally distributed. It isn’t a BLUE requirement, so its absence can’t bias \(\hat\beta\) — but it matters for the confidence intervals and t-tests we build starting next week.

Left: the vertical scatter around the fitted line stays roughly the same width from low x to high x. Right: same fitted line, same overall trend — but the scatter visibly fans out as x grows. That fan is exactly what “the spread of residuals isn’t constant” means.

Prediction and residuals

Fitted values and residuals

\[\hat y_i = \hat\alpha + \hat\beta x_i \qquad e_i = y_i - \hat y_i\]

  • The residual is the vertical distance between a point and the regression line
  • Positive above the line, negative below
  • Residuals from an OLS fit always sum to zero — the line “balances” through the data
  • A direct consequence: average \(\hat y\) equals average \(y\)
{
  const rows = student_summary.filter(d => d.finger_mm != null && !isNaN(d.finger_mm))
  if (rows.length < 3) return html`<p style="color:#aaa;">Not enough data yet.</p>`
  const xbar = d3.mean(rows, d => d.finger_mm), ybar = d3.mean(rows, d => d.mean_rt)
  const cov = d3.mean(rows, d => (d.finger_mm - xbar) * (d.mean_rt - ybar))
  const varx = d3.mean(rows, d => (d.finger_mm - xbar) ** 2)
  const beta = cov / varx
  const alpha = ybar - beta * xbar
  const segments = rows.map(d => {
    const yhat = alpha + beta * d.finger_mm
    return { x: d.finger_mm, y1: d.mean_rt, y2: yhat, sign: d.mean_rt >= yhat ? "positive residual (above line)" : "negative residual (below line)" }
  })
  const xExtent = d3.extent(rows, d => d.finger_mm)
  const fitLine = xExtent.map(x => ({ finger_mm: x, fit: alpha + beta * x }))
  return Plot.plot({
    height: 220, marginLeft: 60,
    x: { label: "Finger length (mm)" }, y: { label: "Reaction time (ms)" },
    color: { legend: true, domain: ["positive residual (above line)", "negative residual (below line)"], range: ["#457b9d", "#e63946"] },
    marks: [
      Plot.line(fitLine, { x: "finger_mm", y: "fit", stroke: "#1a1a2e", strokeWidth: 2 }),
      Plot.link(segments, { x1: "x", y1: "y1", x2: "x", y2: "y2", stroke: "sign", strokeWidth: 1.5, strokeDasharray: "3,2" }),
      Plot.dot(rows, { x: "finger_mm", y: "mean_rt", fill: "#1a1a2e", r: 4 }),
    ]
  })
}

Each dashed segment is one student’s residual — the gap between their actual mean reaction time and the line’s prediction for their finger length.

Interpolation vs. extrapolation

Using the fitted line: predict the mean reaction time for a finger length within the range we observed, then for one far outside it (e.g. 40mm or 110mm).

Interpolation — predicting within the range of x we’ve actually seen — is reasonably safe. Extrapolation — predicting beyond it — assumes the same straight-line pattern keeps holding somewhere we’ve never checked. For a screening tool HR might apply to any candidate, that assumption is doing a lot of unexamined work.

How good is the fit?

R-squared

\[R^2 = \frac{Var[\hat y]}{Var[y]} = 1 - \frac{Var[e]}{Var[y]}\]

Decomposing the total variation in y into what the regression explains and what’s left over:

\[Var[y] = Var[\hat y] + Var[e]\]

  • \(R^2 = 0\): predicted values are just \(\bar y\) for everyone — the regression explains nothing
  • \(R^2 = 1\): every point sits exactly on the line
  • For simple regression: \(R^2 = (Corr[x,y])^2\) — a direct callback to Week 3

R-squared

You’ll also see this written as sums of squares rather than variances — same identity, just without dividing by \(n\). Software output (statsmodels, R, Excel) almost always uses this version:

\[\underbrace{\textstyle\sum(y_i-\bar y)^2}_{TSS} \;=\; \underbrace{\textstyle\sum(\hat y_i-\bar y)^2}_{ESS} \;+\; \underbrace{\textstyle\sum e_i^2}_{RSS} \qquad R^2 = \frac{ESS}{TSS} = 1 - \frac{RSS}{TSS}\]

TSS (total), ESS (explained), RSS (residual) — watch out, some textbooks swap the last two labels (calling the residual part “SSE”). Check what a given source means before trusting the letters alone.

Open the Colab notebook and fit mean_rt ~ finger_mm on the class’s own data with smf.ols(...). Pull out the fitted values, then use them to work out Var[ŷ] and Var[y] yourself — and use those two numbers to compute R².

{
  const rows = student_summary.filter(d => d.finger_mm != null && !isNaN(d.finger_mm))
  if (rows.length < 3) return html`<p style="color:#aaa;">Not enough data yet.</p>`
  const xbar = d3.mean(rows, d => d.finger_mm), ybar = d3.mean(rows, d => d.mean_rt)

  const varx = d3.mean(rows, d => (d.finger_mm - xbar) ** 2)
  const beta = cov / varx, alpha = ybar - beta * xbar
  const fitted = rows.map(d => alpha + beta * d.finger_mm)

  const varYhat = d3.mean(fitted, f => (f - ybar) ** 2)
  const r2 = varYhat / varY
  return html`<p style="font-family:sans-serif;font-size:1.1em;"><strong>R² = ${r2.toFixed(3)}</strong> — the regression explains about ${(r2*100).toFixed(1)}% of the variation in reaction time. Check it against what your own Colab notebook gave you.</p>`
}

That number is the answer to the HR question. R² and correlation are directly linked for simple regression (\(R^2 = Corr[x,y]^2\)) — whatever finger length’s correlation with reaction time turned out to be for our class, this is exactly what it’s worth as a predictor. The formula exists; whether it’s useful is a separate question.

Functional form, briefly

Logs, revisited

Week 3’s online session logged reaction time because it’s skewed. In a regression, which variable you log changes what the slope means:

Model Interpretation of β
Level–level 1-unit x → unit change in y
Log–level 1-unit x → % change in y
Level–log 1% change in x → unit change in y
Log–log 1% change in x → % change in y (elasticity)

Polynomials and splines can capture curvature a straight line misses — useful when prediction is the goal, but each added flexibility costs interpretability. Simpler is usually better; see the textbook for splines, we won’t build them live.

Source: Békés & Kézdi (2021), Ch. 7 & 8

Extreme values — and is it causal?

Influential observations

An observation is influential if including or excluding it noticeably moves the regression line — not the same as simply being an extreme value.

Same three-way decision as Week 1’s outliers: error → fix or drop; real but irrelevant to the question → drop, with a note; genuine feature of the process → keep. Try a transformation before ever dropping a point.

Watch one point move the line

viewof add_extreme = Inputs.toggle({ label: "Add one extreme student", value: false })
{
  const rows = student_summary.filter(d => d.finger_mm != null && !isNaN(d.finger_mm))
  if (rows.length < 3) return html`<p style="color:#aaa;">Not enough data yet.</p>`

  const fit = data => {
    const xbar = d3.mean(data, d => d.finger_mm), ybar = d3.mean(data, d => d.mean_rt)
    const cov = d3.mean(data, d => (d.finger_mm - xbar) * (d.mean_rt - ybar))
    const varx = d3.mean(data, d => (d.finger_mm - xbar) ** 2)
    const beta = cov / varx
    return { alpha: ybar - beta * xbar, beta }
  }

  const xExtentBase = d3.extent(rows, d => d.finger_mm)
  const extreme = { student_name: "Extreme (hypothetical)", finger_mm: xExtentBase[1] + 8,
                     mean_rt: d3.min(rows, d => d.mean_rt) - 40 }
  const withExtreme = add_extreme ? [...rows, extreme] : rows

  const base = fit(rows)
  const withFit = fit(withExtreme)
  const xr = d3.extent(withExtreme, d => d.finger_mm)
  const baseLine = xr.map(x => ({ x, y: base.alpha + base.beta * x }))
  const withLine = xr.map(x => ({ x, y: withFit.alpha + withFit.beta * x }))

  return html`<div>
    ${Plot.plot({
      height: 480, marginLeft: 60,
      x: { label: "Finger length (mm)" }, y: { label: "Mean reaction time (ms)" },
      marks: [
        Plot.dot(rows, { x: "finger_mm", y: "mean_rt", fill: "#1a1a2e", r: 4 }),
        add_extreme ? Plot.dot([extreme], { x: "finger_mm", y: "mean_rt", fill: "#e63946", r: 7, symbol: "diamond" }) : null,
        Plot.line(baseLine, { x: "x", y: "y", stroke: "#999", strokeDasharray: "4,3", strokeWidth: 2 }),

One synthetic point — an implausible combination of very long fingers and a very fast reaction time — is enough to swing \(\hat\beta\), sometimes even flip its sign. That’s leverage: a point far from \(\bar x\) has an outsized say in where the line goes, regardless of whether it fits the pattern the rest of the data shows.

Is it causal?

The slope isn’t zero in our data. Gabor & Kézdi’s list of why, not mutually exclusive:

  • x causes y — longer fingers → faster reactions?
  • y causes x — implausible here, but always worth ruling out explicitly
  • A third variable causes both — hand size, age, or general dexterity could plausibly move both finger length and reaction time together

“Correlation doesn’t imply causation” undersells it. Better: we should not infer cause and effect from a comparison in observational data — not because the method is broken, but because nothing about it was designed to rule out the third alternative.
