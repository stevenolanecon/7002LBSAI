Model problems & inference

Week 4 gave HR a formula. Before anyone trusts it: is it the right shape? What if something’s mismeasured? And how sure are we, really?

From formula to trustworthy formula

HR has last week’s line: reaction time as a function of finger length. Someone on the team asks — can we ship this?

Naive answer: the model’s built, R² is computed, we’re done.

Why it’s not that simple: we assumed a straight line without checking if that’s the right shape. We assumed our measurements are exact. And we’ve given HR one number for \(\hat\beta\) with no sense of how much it could be wrong by. Today, we think about how to fix these issues.

Choosing the right functional form

Recap: why we log

Week 3’s online session showed logging turns differences into approximate percentages, for small changes. That’s the tool — today is about knowing when and how to use it, and what else is in the toolbox.

Source: Week 3 online session

Interpreting log models — the full picture

The table you previewed in Week 4, with the equation behind each row and the reasoning behind each interpretation:

Model Equation Interpretation of \(\hat\beta\)
Level–level \(y^E = \alpha + \beta x\) 1-unit higher x → \(\hat\beta\)-unit higher y, on average
Log–level \(\ln(y)^E = \alpha + \beta x\) 1-unit higher x → \(100\times\hat\beta\) % higher y, on average
Level–log \(y^E = \alpha + \beta \ln(x)\) 1% higher x → \(\hat\beta/100\)-unit higher y, on average
Log–log \(\ln(y)^E = \alpha + \beta \ln(x)\) 1% higher x → \(\hat\beta\)% higher y, on average — an elasticity

Which one to use is a substantive question first: is x likely to move y in multiplicative steps (percentages) or additive ones (fixed amounts)? Only then check whether the distributions agree.

Source: Békés & Kézdi (2021), Ch. 8

When you can’t just log

Logging needs a strictly positive variable — never zero, never negative. Real data often isn’t:

  • Create a binary indicator, then log what’s left — e.g. “is wealth negative?” (0/1), “is wealth zero?” (0/1), and log the positive values, replacing the log with zero where it can’t be taken
  • Add a constant, \(\ln(x+1)\), if x is zero or positive — a common shortcut, but not principled; it’s least distorting when x tends to be large (there, \(\ln(x)\approx\ln(x+1)\) anyway)

Suppose a trial recorded exactly 0ms — a device timing glitch, not a real reaction. Would you drop it, indicator-and-log it, or use \(\ln(x+1)\)? What does your answer depend on?

Source: Békés & Kézdi (2021), Ch. 8

Ratios and per-capita measures

A common transform outside our own dataset: normalising a total by a size variable — GDP/capita, revenue/employee, sales/store.

\[\ln\left(\frac{GDP}{Population}\right) = \ln(GDP) - \ln(Population)\]

The log of a ratio is just the difference of the two logs — so a per-capita measure and its log both stay easy to interpret and combine with everything else you’ve learned about logs today.

Source: Békés & Kézdi (2021), Ch. 8

Polynomials

A quadratic lets the slope change smoothly, without deciding where it bends:

\[y^E = \alpha + \beta_1 x + \beta_2 x^2\]

  • \(\alpha\): average y when x = 0
  • \(\beta_1\) alone has no clean interpretation
  • \(\beta_2\): shape only — U-shaped (convex) if positive, inverted-U (concave) if negative
  • The slope at any point x is \(\beta_1 + 2\beta_2 x\) — it changes as x changes

A trade-off, not a downside: what this gives up in flexibility, it gains back in a coefficient you can actually explain.

Source: Békés & Kézdi (2021), Ch. 8

Fitting a quadratic to our own data

{
  const rows = student_summary.filter(d => d.finger_mm != null && !isNaN(d.finger_mm))
  if (rows.length < 5) return html`<p style="color:#aaa;">Not enough data yet.</p>`
  const x = rows.map(d => d.finger_mm), y = rows.map(d => d.mean_rt)
  const n = x.length
  const s = k => d3.sum(x.map(xi => xi ** k))
  const sxy = k => d3.sum(x.map((xi, i) => xi ** k * y[i]))
  // Normal equations for y = a + b1*x + b2*x^2, solved via Cramer's rule
  const M = [[n, s(1), s(2)], [s(1), s(2), s(3)], [s(2), s(3), s(4)]]
  const v = [d3.sum(y), sxy(1), sxy(2)]
  const det3 = m => m[0][0]*(m[1][1]*m[2][2]-m[1][2]*m[2][1]) - m[0][1]*(m[1][0]*m[2][2]-m[1][2]*m[2][0]) + m[0][2]*(m[1][0]*m[2][1]-m[1][1]*m[2][0])
  const D = det3(M)
  const withCol = (m, col, vec) => m.map((row, i) => row.map((val, j) => j === col ? vec[i] : val))
  const a = det3(withCol(M, 0, v)) / D
  const b1 = det3(withCol(M, 1, v)) / D
  const b2 = det3(withCol(M, 2, v)) / D
  const fitted = x.map(xi => a + b1 * xi + b2 * xi ** 2)
  const ybar = d3.mean(y)
  const varY = d3.mean(y.map(yi => (yi - ybar) ** 2))
  const varYhat = d3.mean(fitted.map(f => (f - ybar) ** 2))
  const r2quad = varYhat / varY
  const xbar = d3.mean(x)
  const cov = d3.mean(x.map((xi, i) => (xi - xbar) * (y[i] - ybar)))
  const varx = d3.mean(x.map(xi => (xi - xbar) ** 2))
  const betaLin = cov / varx, alphaLin = ybar - betaLin * xbar
  const fittedLin = x.map(xi => alphaLin + betaLin * xi)
  const varYhatLin = d3.mean(fittedLin.map(f => (f - ybar) ** 2))
  const r2lin = varYhatLin / varY
  const grid = d3.range(d3.min(x), d3.max(x), (d3.max(x) - d3.min(x)) / 60)
  const curve = grid.map(xi => ({ finger_mm: xi, fit: a + b1 * xi + b2 * xi ** 2 }))
  const chart = Plot.plot({
    height: 420, marginLeft: 60,
    x: { label: "Finger length (mm)" }, y: { label: "Mean reaction time (ms)" },
    marks: [
      Plot.dot(rows, { x: "finger_mm", y: "mean_rt", fill: "#1a1a2e", r: 4 }),
      Plot.line(curve, { x: "finger_mm", y: "fit", stroke: "#e63946", strokeWidth: 2.5 }),
    ]
  })
  return html`<div>${chart}<p style="font-family:sans-serif;font-size:1em;text-align:center;">Linear R² = <strong>${r2lin.toFixed(3)}</strong> &nbsp;·&nbsp; Quadratic R² = <strong>${r2quad.toFixed(3)}</strong></p></div>`
}

Does the quadratic noticeably beat the straight line? If the improvement is tiny, that’s a finding too — it says the relationship really is close to linear, for this data.

The roadmap for choosing a functional form

  1. Check the distributions of y and x — skewed, long right tail?
  2. Look at the shape — scatterplot or a non-parametric fit (bin-scatter, lowess)
  3. Choose a transform to match what you see — and remember: not every variable can sensibly be logged or ratio’d
  4. Compare models — if the results agree, that’s a robustness check; if they disagree sharply, find out why

Extreme values and influence

Extreme value ≠ influential observation

An extreme value is just unusual on some variable. An influential observation is one whose presence or absence noticeably moves the regression line.

Every influential observation is extreme on something — but plenty of extreme values sit right near the line and barely matter. The two ideas get conflated; they shouldn’t be.

Source: Békés & Kézdi (2021), Ch. 8

What to do — and it depends which variable

  • General rule: avoid dropping observations based on their y value. A genuinely strange outcome is still information — dropping it because it’s inconvenient biases what’s left
  • Dropping on x can be more defensible — if that x value is atypical for the question you’re asking
  • But often the opposite is true: extreme x values are the most informative ones, since they’re where you see the most variation in the pattern
  • Always try a transformation before ever dropping a point

Source: Békés & Kézdi (2021), Ch. 8

Measurement error

Nothing here is measured exactly

Every number in our dataset carries some noise:

  • Reaction time — self-timed by students on their own devices, with browser and reflex lag
  • Finger length — self-measured with a ruler, to the nearest millimetre, by hand

This isn’t a flaw specific to our exercise — almost all data in business and economics is measured with error. The question isn’t whether it exists, but what it does to \(\hat\beta\).

Classical measurement error

A measured variable equals its true value plus noise: \(x = x^* + e\)

Classical measurement error: (1) averages to zero — it doesn’t shift the variable’s mean — and (2) is independent of everything else in the model, including the true value itself.

Recording slips, rounding, reflex-timing lag — plausibly classical. A systematically miscalibrated ruler would not be.

Source: Békés & Kézdi (2021), Ch. 8

Noise in y doesn’t bias the slope

If only the dependent variable is measured with classical error, \(y = y^* + e\):

\[\hat\beta = \frac{Cov[y,x]}{Var[x]} = \frac{Cov[y^*+e,\ x]}{Var[x]} = \frac{Cov[y^*,x] + Cov[e,x]}{Var[x]} = \frac{Cov[y^*,x]}{Var[x]} = \hat\beta^*\]

\(Cov[e,x]=0\) by the classical assumption, so it drops straight out. Noisy y makes the fit worse — more scatter around the line — but it doesn’t move \(\hat\beta\) on average.

Noise in x does — attenuation bias

If the explanatory variable is measured with classical error, \(x = x^*+e\), the noise inflates \(Var[x]\) itself:

\[\hat\beta = \hat\beta^* \times \frac{Var[x^*]}{Var[x^*] + Var[e]}\]

That fraction is always less than one — so \(\hat\beta\) is always pulled toward zero, never away from it. This is attenuation bias. The noisier x is relative to its real variation, the flatter the estimated slope looks, regardless of the true relationship.

Source: Békés & Kézdi (2021), Ch. 8

\(\hat\beta\) shrinks toward zero as noise is added to finger length — but it never crosses zero, no matter how much noise is added. \(Var[x^*]/(Var[x^*]+Var[e])\) is always between 0 and 1, so attenuation can flatten the line but can never flip its sign.

Noise-to-signal ratio

\[\text{noise-to-signal} = \frac{Var[e]}{Var[x^*]}\]

  • Low ratio — recording is careful, or the variable is an aggregate over a large sample. Often safe to ignore
  • High ratio — the noise added is large relative to the real spread in x. Worth taking seriously, and worth being upfront about in any write-up

You can rarely eliminate measurement error. You can almost always say something honest about its likely direction — and for x, that direction is always toward zero.

Generalising this regression

How sure are we about β̂?

Week 2 built a confidence interval for a mean. Exactly the same logic now applies to a slope:

\[CI(\hat\beta)_{95\%} = \left[\hat\beta - 2\,SE(\hat\beta),\ \ \hat\beta + 2\,SE(\hat\beta)\right]\]

Same idea as \(CI(\bar x) = \bar x \pm 2\,SE(\bar x)\) from Week 2 — a plausible range for the true slope, built from how much \(\hat\beta\) would bounce around across repeated samples.

Source: Békés & Kézdi (2021), Ch. 9

Where SE(β̂) comes from

\[SE(\hat\beta) = \frac{Std[e]}{\sqrt{n}\cdot Std[x]}\]

SE(β̂) is smaller — the estimate more precise — when:

  • Std[e] is small — the line fits well, little left-over scatter
  • Std[x] is large — x varies a lot in the data
  • n is large — more observations

Notice: this is the same \(Std[e]\) and \(Std[x]\) from Week 4’s slope formula. Precision and the estimate itself come from the same ingredients.

Source: Békés & Kézdi (2021), Ch. 9

Task — SE and CI for our own regression

By hand or in Excel: using the SE(β̂) formula from the last slide and β̂ from Week 4, calculate the 95% CI for our own finger-length regression.

{
  const rows = student_summary.filter(d => d.finger_mm != null && !isNaN(d.finger_mm))
  if (rows.length < 4) return html`<p style="color:#aaa;">Not enough data yet.</p>`
  const x = rows.map(d => d.finger_mm), y = rows.map(d => d.mean_rt)
  const n = x.length
  const xbar = d3.mean(x), ybar = d3.mean(y)
  const cov = d3.mean(x.map((xi, i) => (xi - xbar) * (y[i] - ybar)))
  const varx = d3.mean(x.map(xi => (xi - xbar) ** 2))
  const beta = cov / varx, alpha = ybar - beta * xbar
  const resid = x.map((xi, i) => y[i] - (alpha + beta * xi))
  const sdE = Math.sqrt(d3.sum(resid.map(e => e ** 2)) / (n - 2))
  const sdX = Math.sqrt(varx)
  const seBeta = sdE / (Math.sqrt(n) * sdX)
  const lo = beta - 2 * seBeta, hi = beta + 2 * seBeta
  return html`<p style="font-family:sans-serif;font-size:1.1em;">
    β̂ = <strong>${beta.toFixed(3)}</strong> &nbsp;·&nbsp; SE(β̂) = <strong>${seBeta.toFixed(3)}</strong><br>
    95% CI: <strong>[${lo.toFixed(3)}, ${hi.toFixed(3)}]</strong></p>`
}

Left: residual spread constant across x. Right: residual spread fans out as x grows — the fit gets less precise for larger x, but OLS’s classical SE formula doesn’t know that.

In practice this is often false — the fit may be tighter for some x values than others. The fix is heteroskedasticity-robust SE (White/Huber), correct either way — but you have to ask for it. Software doesn’t default to it: statsmodels, R, and Excel all give you the classical formula above unless you explicitly request the robust version.

import statsmodels.formula.api as smf

model = smf.ols('reaction_time_ms ~ device', data=df).fit(cov_type='HC1')

Add cov_type='HC1' to .fit() and every SE, CI, and p-value that comes out the other end is heteroskedasticity-robust. Practical rule: use it by default; it costs nothing when homoskedasticity holds, and saves you when it doesn’t.

Source: Békés & Kézdi (2021), Ch. 9

Testing if β is really zero

\[H_0: \beta_{true} = 0 \qquad H_A: \beta_{true} \neq 0 \qquad\qquad t = \frac{\hat\beta}{SE(\hat\beta)}\]

  • \(t \approx 2\) corresponds to the 95% CI boundary — the same threshold, from a different angle
  • A coefficient is “statistically significant” if its CI doesn’t contain zero — most commonly at the 5% level (\(p<0.05\))

This is the exact same t-statistic logic as Week 2’s tea test — just applied to a slope instead of a mean difference.

Source: Békés & Kézdi (2021), Ch. 9

Two different questions about prediction

  • Confidence interval for the predicted value — where do we expect the average y to be, for a given x? Uncertainty about \(\hat\alpha\) and \(\hat\beta\) only
  • Prediction interval — where do we expect one particular y to actually land, for a given x? Adds the extra spread of individual observations around their own average

The CI narrows toward zero as n grows. The PI never does — no amount of data removes the fact that individuals vary around the average.

Source: Békés & Kézdi (2021), Ch. 9

Both bands, on our own data

{
  const rows = student_summary.filter(d => d.finger_mm != null && !isNaN(d.finger_mm))
  if (rows.length < 4) return html`<p style="color:#aaa;">Not enough data yet.</p>`
  const x = rows.map(d => d.finger_mm), y = rows.map(d => d.mean_rt)
  const n = x.length
  const xbar = d3.mean(x), ybar = d3.mean(y)
  const cov = d3.mean(x.map((xi, i) => (xi - xbar) * (y[i] - ybar)))
  const varx = d3.mean(x.map(xi => (xi - xbar) ** 2))
  const beta = cov / varx, alpha = ybar - beta * xbar
  const resid = x.map((xi, i) => y[i] - (alpha + beta * xi))
  const sdE = Math.sqrt(d3.sum(resid.map(e => e ** 2)) / (n - 2))
  const grid = d3.range(d3.min(x) - 1, d3.max(x) + 1, (d3.max(x) - d3.min(x) + 2) / 60)
  const bands = grid.map(x0 => {
    const fit = alpha + beta * x0
    const seFit = sdE * Math.sqrt(1 / n + ((x0 - xbar) ** 2) / (n * varx))
    const sePred = sdE * Math.sqrt(1 + 1 / n + ((x0 - xbar) ** 2) / (n * varx))
    return { x: x0, fit, ciLo: fit - 2 * seFit, ciHi: fit + 2 * seFit, piLo: fit - 2 * sePred, piHi: fit + 2 * sePred }
  })
  return Plot.plot({
    height: 440, marginLeft: 60,
    x: { label: "Finger length (mm)" }, y: { label: "Mean reaction time (ms)" },
    marks: [
      Plot.areaY(bands, { x: "x", y1: "piLo", y2: "piHi", fill: "#457b9d", fillOpacity: 0.12 }),
      Plot.areaY(bands, { x: "x", y1: "ciLo", y2: "ciHi", fill: "#e63946", fillOpacity: 0.25 }),
      Plot.line(bands, { x: "x", y: "fit", stroke: "#1a1a2e", strokeWidth: 2 }),
      Plot.dot(rows, { x: "finger_mm", y: "mean_rt", fill: "#1a1a2e", r: 4 }),
    ]
  })
}

The narrow red band is the CI of the regression line; the wide blue band is the prediction interval. For a new student HR hasn’t met yet, which band should they actually use to set expectations? Why is it so much wider?
